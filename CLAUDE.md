# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Publishing, licence and contributions

nembot is published under the PolyForm Noncommercial License 1.0.0 (`LICENSE`); commercial licences are sold separately, so outside pull requests aren't accepted (`CONTRIBUTING.md`) until there's a contributor licence agreement. Commit on branches; never push, tag or publish without the user asking. Open TODOs and known issues are in `ROADMAP.md`. If a `plan.md` exists it is the user's private planning notes (gitignored, never commit it): read it for decisions and context. Keep AEMO's credit line on every export (`attribution.CREDIT`).

## Commands

Python >=3.14, managed with `uv`. Tests use stdlib `unittest` (no pytest).

```bash
uv run python -m unittest discover -s tests                  # all tests (plain `-m unittest` finds none)
uv run python -m unittest discover -s tests -k test_name      # single test by name substring
uv run python scripts/build_catalog.py                       # rebuild catalog.json from the data-model PDF
uv run nembot --start 2026-06-01 --end 2026-08-31            # load data (defaults: data/nem.duckdb, data/cache)
uv run nembot-chat                                           # web chat at http://127.0.0.1:8000 (--port, --database)
uv run marimo edit load_mms.py                               # original notebook chat (OpenRouter)
```

`load_mms.py` imports `polars` and `pydantic_ai`, which are **not** declared in `pyproject.toml`; supply them (e.g. `uv run --with polars --with pydantic-ai ...`) to run the notebook. The web chat needs only declared deps plus at least one connected AI service, set up on its Settings page (`#setup`, opened automatically on first run) or by environment variables (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `DEEPSEEK_API_KEY`) or an `ant auth login` profile. The Claude plan option needs `claude_plan = true` in `~/.config/nembot/credentials.toml`. To try a fresh install without touching your setup, run a second copy with `NEMBOT_CONFIG_DIR`, `ANTHROPIC_CONFIG_DIR` (an empty dir), `--port`, `--database` and `--cache-dir` pointing at temp dirs and the API key variables unset.

## Architecture

Three pieces share the DuckDB file `data/nem.duckdb` (`data/` and `__marimo__/` are gitignored):

1. **`src/nembot/` — the ingest package** (public API: `load_mms`, CLI: `nembot`).
   - `catalog.json` + `catalog.py` — the data-model catalogue for all 571 tables: package, comment, description, visibility, primary key, indexes, columns with Oracle and DuckDB types, and whether the latest MMSDM monthly archive publishes the table. It's generated from AEMO's Electricity Data Model Report **PDF** by `uv run python scripts/build_catalog.py` (pdfplumber is a dev dependency; the build takes about 2 minutes, needs network, and fails loudly via `problems`). Never hand-edit the JSON. One data-model version (currently 5.7) is used for both docs and loader schemas.
   - `tables.py` — `Table` schemas generated from the catalogue: ordered columns → DuckDB types, plus the primary key. The CSV envelope identity (dataset/csv_table) is only known for the four `DEFAULT_TABLES`; for other tables `nemweb.normalize` takes it from the archive's first `I` record and errors if an archive mixes tables. The loader accepts only `ingest.SUPPORTED` tables until its window filtering is generalised.
   - `nemweb.py` — all HTTP goes through `_polite()` → `_open()`, a shared keep-alive urllib3 pool that raises urllib-style `HTTPError`/`URLError`. Tests patch `nembot.nemweb._open` with a fake NEMWEB server. A process-wide `_Throttle` allows `CONCURRENCY` requests (default 2, env `NEMBOT_CONCURRENCY`, capped at 3) and paces request starts AutoThrottle-style (latency ÷ concurrency, with optional floor `REQUEST_INTERVAL`). Errors (429/5xx/connection) drop to one request at a time with backoff and `Retry-After`, recovering after `RECOVER_AFTER` successes; `FORBIDDEN_LIMIT` consecutive 403s abort the run. `download_many()` downloads a few files ahead in parallel and yields them in order; both loaders use it. Directory listings are cached in memory for an hour (tests call `nemweb.clear_cache()`). It scrapes MMSDM HTML directory listings to discover monthly per-table ZIPs, downloads them into `cache_dir` (validated, SHA256'd, reused on rerun), and `normalize()` strictly validates the MMS C/I/D CSV envelope (opening C record, END OF REPORT count, integer versions, known columns, PK present), emitting one clean CSV per `I` header segment. Decimals with more fractional digits than the data model documents (AEMO's 2024 DISPATCHPRICE has 6 in `CUMUL_PRE_AP_ENERGY_PRICE`, documented as DECIMAL(15,5)) are rounded half up, as AEMO's Oracle stores them, and counted per column (`normalize(..., rounded=)`); ingest records each file's counts in `_nembot.notes` (url, table_name, note), prints them, sends a `note` progress event (kept in `Job.notes`), and the Explorer lists them under "Loading notes". Anything else invalid, including values too large after rounding, still rejects the file.
   - `ingest.py` — orchestration. Market time is fixed UTC+10. Each (table, file) is loaded in its own transaction and recorded in `_nembot.files` keyed by (url, sha256, table, window) so reruns skip completed work and interrupted runs resume. `_merge` stages typed CSVs, picks the latest `LASTCHANGED` per PK, raises on equal-`LASTCHANGED` conflicts (both within a file and against stored rows), and only updates rows with strictly newer `LASTCHANGED`.
   - `DUDETAILSUMMARY` is special-cased: it's effective-dated reference data, so all monthly snapshots are reconciled together in a temp `_reference` table *before* the date-window overlap filter is applied (otherwise later closures could resurrect old rows). Interval tables are window-filtered per file.
   - `cli.py` — argparse + TOML config (`--config`); config keys mirror flags, flags override config, and config is validated even when overridden.
   - `load_mms()` loads any table in `ingest.SUPPORTED` (every catalogue table the monthly archive publishes). `EXACT_WINDOW` tables (DISPATCHPRICE, DISPATCHREGIONSUM, DISPATCH_UNIT_SCADA) are filtered to the exact market days requested; every other table loads **whole archive months** (the file log records month windows), because timestamp meanings vary by table. Tables without `LASTCHANGED` are updated by the most recently loaded archive. Timestamps parse with or without milliseconds (`TIMESTAMP(n)` columns).
   - With no `connection=`, `load_mms()` opens and returns a writable connection the caller must close. With one (the web app), it runs on a cursor of that connection and returns it. `progress=` receives stage events and `cancel=` (a `threading.Event`) aborts with `nemweb.Cancelled`. Each file commits on its own, so finished files survive a cancel or a failure. DuckDB allows one writer per database file, so the CLI can't run while the web app has the database open. The web app checkpoints on shutdown so restarts don't depend on replaying the WAL: DuckDB 1.5 writes an unreplayable WAL for `ALTER TABLE` on a table whose rows are still only in a replayed WAL, so don't add ALTER-based migrations to the `ensure()` functions (temp tables are fine).

   - `live.py` — recent data from NEMWEB's report feeds (newer than the monthly archive) for the tables in `FEEDS`, each mapped to a report family, file prefix and CSV identity (verified against live files). An ARCHIVE file covers from its date to the next archive file's date, or to an explicit second date for weekly files. Separate filename series, e.g. rooftop MEASUREMENT vs SATELLITE, are handled independently. CURRENT files fill in after the newest archive, but only up to `CURRENT_LIMIT` (600) requests; beyond that the plan stops at the archive's end and reports `skipped_current`. `nemweb.normalize` descends into nested ZIPs (daily archives hold 288 interval ZIPs), merges all members into one output per table version, and with `required=False` tolerates files without the table. Live files are logged in `_nembot.files` with their coverage window. "Loaded through" comes from the table's own max time column, not from file URLs.

2. **`load_mms.py` — a marimo notebook** (despite the name, it does not load data). It opens the DB `read_only=True` and runs a pydantic-ai agent (via OpenRouter, `OPENROUTER_API_KEY`) inside `mo.ui.chat`, exposing two tools: `query_mms(sql)` and `visualize_mms(sql, plot_spec)` (Vega-Lite validated with Altair before running SQL, rendered to PNG for the model). The `SYSTEM_PROMPT` cell defines agent behavior.

3. **The web chat** (`nembot-chat`): a port of the notebook that can use any Claude model directly or any tool-capable OpenRouter model, switching freely mid-conversation.
   - `chat.py` — the provider-neutral core: system prompt (vision and text-only variants), tool schemas, DuckDB tool execution, and `run_turn` (the tool loop, sequential tool calls, rollback of a failed turn). History is stored in a **neutral format** (documented at the top of the file); plot PNGs are always stored and only sent to models that can read images.
   - `claude.py` / `openai_compat.py` / `ollama.py` — each provider renders neutral history into its wire format and streams one assistant turn. Rendering must stay **deterministic per (history, current model)** so turns replay byte-identically (prompt caching, and Claude's preserved-thinking check). Same-model turns replay provider raw data (Claude content blocks with thinking; OpenRouter `reasoning_details`); turns from other models are rendered from neutral fields and prefixed `[Earlier reply by …]`. Claude per-model request features (adaptive thinking, `display: "updates"`, effort, `fallbacks: "default"`) are gated by `request_options()`.
   - `subscription.py` — Claude through the user's Claude plan via the Claude Agent SDK (Anthropic allows a subscription through the SDK, not by calling the API with its login). The SDK runs its own loop, so the provider bridges it to `run_turn`: one SDK session per user turn (keyed by `id(history)`), nembot's tools exposed as in-process MCP tools whose handlers wait until `run_turn` has run the calls and `respond` hands back the results; `run_turn`'s `finally` calls `close_turn` to end an abandoned session. Claude Code's own tools are off (WebSearch/WebFetch only with web search) and no settings are loaded; the system prompt gets a note that tools carry the `mcp__nembot__` prefix (without it models sometimes call `query_mms` and fail). Sessions are saved with `cwd` = `<database dir>/claude-sessions` (so Claude Code files them under ~/.claude/projects/…-claude-sessions). A turn following this model's own finished turn resumes that turn's session with `fork_session` (the old session stays intact, so a failed or stopped turn that `run_turn` drops never leaks into the next) and sends only the new message; the final turn stores `raw['subscription'] = {'session', 'parent'}`, and resuming deletes the parent's parent. Otherwise (first message, another model last, a stopped turn, a session Claude Code cleaned up) earlier turns go as a text transcript (`render_prompt`). Deleting a chat deletes its sessions (`forget_chat`). Usage events carry `plan: true` and no cost. `MCP_TOOL_TIMEOUT` is raised so download approvals can wait. Tests fake Claude Code (`tests/test_subscription.py`).
   - Web search (UI toggle, default on) adds Anthropic's server-side `web_search`/`web_fetch` tools (`_20260209` dynamic-filtering versions where supported, gated in `claude.web_tools()`) or OpenRouter's `openrouter:web_search` server tool. Neither runs in our tool loop. With `openrouter:web_search` on, OpenRouter doesn't stream: reasoning and text arrive in one piece at the end (checked 2026-10-26; its `web` plugin streams but searches on every request, so it was rejected). The composer shows a note (`#search-note`) while web search is on and an OpenRouter model will answer, and the reasoning dropdown times from the event before it so "Reasoned for N s" stays right. Sources are emitted as a `sources` event: Claude citations, or the consulted pages when dynamic filtering leaves the text uncited.
   - Usage and cost: each provider request yields a `usage` event (new/cached/written input tokens, output tokens, web searches, cost, generation seconds from first output to end). Claude costs come from the price table in `pricing.py` (from the pricing page, dated; update it when prices change), priced by the model that actually served the request; OpenRouter reports its own cost (falling back to catalogue prices). Usage events are saved in chat transcripts, and `chat.js` totals them per chat in the stats line under the composer. Naming calls (`complete()`) aren't counted.
   - Compare turns: the composer can add up to three more models ("+ compare" in the picker, chips beside the model button; not in Creator mode). `/api/chat` then takes `models` and `chat.run_compare` runs each model's `run_turn` concurrently on its own copy of the conversation (shared `pending`, separate `results`), tagging events with `branch`. The chat continues from the first model that replied (`kept` event), and `POST /api/chat/keep` switches branch until the next turn starts (alternatives live in `Conversation.branches`, in memory only, so switching ends at restart). History stays linear, so replay rules are unchanged. Stop: each running reply is an asyncio task in `Conversation.running` (`None` for a single-model turn run by `chat.run_single`, branch indexes for compare turns); `POST /api/chat/stop` calls `chat.stop_turn` (all, or one `branch`), which sets `stopping` and cancels. A stopped `run_turn` keeps what the model had written plus `[Stopped by the user]` as a plain assistant turn (an unanswered tool call is dropped), so the chat can continue; a cancellation without `stopping` (the browser left) still discards the turn. Events: `stopped` (per branch in compare turns) and the live-only `branch_done`. In the UI, Send becomes ■ Stop while a reply runs, and each compare column has its own Stop. A tool already running in a worker thread (a slow query or plot) finishes in the background; its result is discarded. `chats.compact` only joins text from the same branch; `renderTurn` draws compare turns as columns.
   - `models.py` — `ModelInfo` and the `Catalog`: models from every *connected* source (`Connections._sources`), cached for an hour, `invalidate()`d when onboarding changes a connection; a failing source is reported in `errors` and skipped. `default()` is the first available of `preferred` (Anthropic Opus, plan Opus, each preset's `test_model`), else the first usable model. Model refs are `subscription:<id>` / `claude:<id>` / `<preset>:<id>` (e.g. `ollama:llama3.2:3b`; split on the first colon).
   - Reasoning levels: `ModelInfo.efforts` lists the levels a model takes (lowest first, `models.EFFORT_ORDER`) and `default_effort` is nembot's default (`models.default_effort`: medium, else high, low, or `on`). They're read from each service: the Anthropic models API (`capabilities.effort`), OpenRouter's catalogue (`reasoning.supported_efforts`; with no level sent a model runs at its own default, and Kimi K3.1's is max), Claude Code (`supportedEffortLevels`), and Ollama thinking models (`off`/`on` → `think`). The picker shows level buttons on the hovered, current and compared rows; the choice is remembered per model in localStorage (`efforts`) and sent as `efforts: {ref: level}` with each chat request. `run_turn(efforts=…)` passes `effort` to `provider.respond` only for models with levels (`chat.chosen_effort` falls back to the default); Claude sends `output_config.effort`, OpenRouter `reasoning.effort`, the Claude plan the SDK's `effort`. Replies and compare columns show the level they ran at (`chat.model_event`).
   - Connections and onboarding: `credentials.py` stores keys and settings in `~/.config/nembot/credentials.toml` (or `$NEMBOT_CONFIG_DIR`; dir 0700, file 0600, written atomically by a small TOML writer); environment variables win over stored keys; with `keyring = true` keys live in the OS keychain (optional extra `keyring`; `use_keyring()` moves them). `presets.py` lists the OpenAI-compatible services (OpenRouter, OpenAI, Gemini, DeepSeek, Ollama, LM Studio: address, key env var, key page, `tested`, `test_model`) and lists their models (OpenRouter's catalogue, with a `/key` check because its list is public; Ollama's `/api/show` capabilities; otherwise name heuristics). `openai_compat.py` is the chat adapter for the presets (generalised from the old OpenRouter provider; `openrouter.py` is a shim keeping `OpenRouterProvider()` for the evals plugin). **Ollama uses `ollama.py`** (native `/api/chat`), because its OpenAI-compatible endpoint ignores the context size and runs at the server default (2,048 tokens on 0.34), silently cutting nembot's prompt so the model never sees its tools; the native call sets `options.num_ctx` = 16384 (capped at the model's context; `num_ctx` in `[providers.ollama]` overrides). `connections.py` owns the providers and catalogue, rebuilds the Anthropic client on change (`anthropic_client()` falls back to a placeholder, since the SDK raises at construction when an `ant` profile is broken), and builds the Settings cards. The Claude plan provider is only listed with `claude_plan = true` (Anthropic's terms: offering claude.ai login needs Anthropic's approval). `setup.py` tests a connection without saving (list models, then one tiny tool call with `ping`), explains failures, and runs OpenRouter's OAuth PKCE sign-in (callback `http://localhost:<port>/setup/openrouter/callback`, `state` checked). The `/api/setup*` endpoints are guarded by `setup.refusal()`: loopback clients only, same Origin, JSON bodies. `static/setup.js` is the `#setup` page (cards, connect/test/disconnect, first-data download of the latest month of DISPATCHPRICE and DISPATCHREGIONSUM, keychain toggle); it opens by itself when no usable model is connected. `run_turn` turns web search off for providers without it (`provider.web_search`).
   - `downloads.py` — in-memory download jobs (`kind` 'archive' for monthly MMSDM, 'live' for `live.load`; `submit_live()` plans and queues the recent files) run one at a time by a worker thread via `load_mms` on the app's single read-write connection (chat/explorer reads use their own cursors and see each committed file). It also provides `plan()` (loaded months from `_nembot.files` URLs, latest published month, refresh range, size estimate from listing sizes) and the freshness flags shown in the explorer. Jobs are not resumed after a restart.
   - `web.py` (Starlette) streams UI events as SSE to `static/index.html` (vega-embed, marked, DOMPurify from CDN). Conversations are keyed by a browser-generated id; they are held in memory while in use and saved by `chats.py` (below). Services are connected on the Settings page (or by environment variables).
   - `explorer.py` — the read-only explorer API: overview (catalogue tables in the monthly archive, marked downloaded or not), table details (docs, row count, time-column range, `_nembot.files` download history, filter options) and paged rows. Column names in SQL only ever come from the catalogue; filter values are always parameters. `catalog.time_column()`/`kind()` classify tables as interval, effective-dated or reference. The SQL editor (`#explorer/<TABLE>/sql`, `static/sqleditor.js`) is CodeMirror 6 from esm.sh (core packages imported through the same `^6.0.0` ranges that `lang-sql` uses, so there's one copy of each; highlighting reuses `loadHighlighter()`'s `.tok-*` style) with completion from `/api/explorer/schema` and DuckDB's functions (`/api/explorer/functions`, `explorer.functions` from `duckdb_functions()`, also shown on hover over a call). As you type, `POST /api/explorer/check` (`explorer.check_sql`) has DuckDB parse and bind the query without running it, and the editor underlines what it reports (CodeMirror lint; syntax-error positions from `json_serialize_sql`, binder errors at the name they quote). `POST /api/explorer/sql` (`explorer.run_sql`) runs one read-only SELECT and streams the first `SQL_ROWS` (1000) rows. `@marimo-team/codemirror-sql` was tried and rejected (2026-10-24): it lints with PostgreSQL's grammar and flagged 1 in 8 valid DuckDB queries (GROUP BY ALL, QUALIFY, EXCLUDE, PIVOT).
   - Front end: `static/index.html` is a shell with hash routing (`#chat/<id>`, `#explorer/<TABLE>[/sql]`, `#docs/<id>`, `#snippets/<id>`, `#reports`). The code lives in classic scripts that share globals, loaded in order: `common.js` (helpers), `datatable.js`, `downloads.js` (job polling, header indicator, progress/error panel, month-range dialog), `chat.js`, `explorer.js`, `sqleditor.js`, `snippets.js`, `docs.js`, `chats.js`, `reports.js`, `plugins.js`, plus `app.css`. Plugin tabs route as `#plugin/<plugin>/<tab>`; the management page is `#plugins`. SQL is shown with `codeBlock(code, 'sql')` in `common.js` (`sqlBlock` uses it): CodeMirror's Lezer SQL parser from esm.sh, mapped to marimo's editor colours (`--tok-*` in `app.css`, light and dark). Vega-Lite specs use `jsonTree(value)`, a collapsible tree (`<details>` per object/array, Alt+click folds a whole branch) in the same colours. Charts go through `embedChart`, which redraws them when the light/dark setting changes.
   - Missing data: `describe_table` documents any catalogue table. `request_download` emits a `download_request` event (an approval card in chat), then waits on a Future in `Conversation.pending`, which `POST /api/chat/decision` resolves. On approval it submits a normal download job, streams progress and returns a result telling the model to re-run its query. Each user message stores a frozen `<data_status>` note (`chat.data_status`) of what's downloaded; it's rendered after the user's text and never recomputed, so history replays identically. The archive table list sits in the static system prompt.
   - Questionnaire: in interactive chats (`run_turn(..., interactive=True)`, passed by the chat endpoint; evals and doc asks leave it out so nothing waits unattended) analyst and creator modes get the `questionnaire` tool and `QUESTIONNAIRE_NOTE` in the prompt. The model sends 1-4 multiple-choice questions (2-4 options, optional header and multi-select; `parse_questions` validates and reports problems back as a tool error). A `questions` event draws a card (`questionsCard` in chat.js; every question also has a free-text "Something else" answer), the turn waits on a Future in `Conversation.pending` (30 min, `DECISION_TIMEOUT`) resolved by `POST /api/chat/answer`, then `questions_answered` locks the card and the model gets the answers as text (`answers_text`). Skipping or timing out tells the model to make sensible choices and say what it assumed.
   - Timings: `run_query` records wall-clock `Result.seconds`; table and plot events carry `query_seconds`, and plots `render_seconds` (chart spec plus, in the chat, the PNG for the model; re-runs and snippets time the spec only). `common.js` `timing()` shows them in the SQL/plot summary lines ("SQL query · 3 ms", "query 7 ms, chart 7 ms"); the SQL editor uses the same `formatSeconds`. The server prints every thread's stack on `kill -USR1 <pid>` (faulthandler), for diagnosing a stuck download or request.
   - Scrolling: streaming replies keep `#log` at the bottom only while the reader is there (`followLog`, updated on scroll; reset when sending or switching chats); the reasoning box follows the same rule.
   - `chats.py` — saved chats in `chats.chats`, written after every turn by the chat endpoint: the neutral `history` (replayed to the model when the chat continues, including after a restart), `results` (R ids) and a `transcript` of what the UI showed (`{'text', 'events'}` per turn, compacted by `chats.compact`), which `static/chats.js` replays through `renderTurn(text, {replay: true})` (no side effects; old approval cards are disabled). Charts are saved without their data (`chats.strip_chart_data` drops a plot event's `spec` and `rows`, keeping SQL, `plot_spec` and `total`); `renderPlot` re-runs them through `POST /api/chart` (`chat.rerun_chart`) as they scroll into view, noting the re-run and warning when the row count changed. Only HTML exports inline chart data. Build every chart with `chat.chart_spec()`, which validates the spec on one row: altair's per-row validation took minutes on large results. `web_search` is restored on reopening, because Claude's preserved thinking is bound to the same system prompt and tools. A new chat is named by its model from the first message in parallel with the reply (`chat_title` event); a title the user typed (`title_by_user`) is never overwritten. The Chats column (search, ✎/double-click rename, delete) routes as `#chat/<id>`. Each chat shown in a session has its own pane in `#log` (`panes` in chat.js), so replies keep streaming into their chat while another is on screen; busy chats keep their live pane, finished hidden panes are dropped and replayed from the saved chat if reopened, and the list marks chats that are replying or waiting for an approval (`pane.busy`/`pane.waiting`). Approval cards post their own chat id.
   - `snippets.py` — saved SQL plus an optional Vega-Lite spec (no data) in the `snippets.snippets` table of the same database, created on startup. They're re-run on every open (`/api/snippets/{id}/run`). Names come from the current chat model via each provider's `complete()`, falling back to the table name. `static/snippets.js` adds the "☆ Add to snippets" button to chat results and the Snippets page.
   - Shared documents (`docs.py`, `static/docs.js`): Tiptap (MIT, loaded from esm.sh on first open via dynamic `import()`) rich-text docs in the `docs` schema: `docs.docs` stores Tiptap JSON plus comment threads (JSON), `docs.images` stores pasted/uploaded images (PNG/JPEG/GIF/WebP, never SVG). The browser is the source of truth and autosaves the whole doc; only one editor is open per document (Docs page `#docs/<id>` or the panel beside the chat). Tables and charts are `dataBlock` nodes holding their SQL, spec and a row **snapshot** (`docs.snapshot`; Refresh re-runs it). Highlighting text and choosing "Ask nembot" runs a one-off `run_turn` in `doc` mode with a `DocSession`: the request carries the document as numbered blocks (`[B3]`), and nembot proposes changes with `suggest_edit`/`suggest_insert`/`suggest_table`/`suggest_chart`, which the browser applies as tracked suggestions (`suggestInsert`/`suggestDelete` marks, or a `suggestion` attribute on whole blocks) for the user to accept or reject. Everything nembot writes into a document (insertions, inline rewrites, create_document seeds) travels as **markdown and is rendered in the browser with `marked`**, the chat's renderer, so GFM tables and lists format exactly as in the chat; the editor has Tiptap tables. Inserted content is parsed with `createNodeFromContent` and inserted in one transaction so its size is exact (Tiptap's trailing-node plugin appends steps afterwards). Suggested whole blocks are outlined by a decoration (`nb-suggested-block`), since the table node view ignores attributes. In the main chat, `create_document(title, content)` seeds a doc from markdown with `[[R3]]` lines (`seed`: JSON parts, converted once by the editor), and results get "＋ Add to doc".
   - Reports: each successful query/plot result gets an id (`R1`, … in `Conversation.results`, shown in its tool output and UI). `create_report(format, title, content)` takes markdown with `[[R3]]` lines. `reports.py` re-runs the referenced SQL and builds html (interactive vega-embed), pdf (WeasyPrint, static PNGs), docx, pptx (a slide per `##` section), xlsx (a sheet per result) or Jupyter/marimo notebooks into `<database dir>/reports/`.
   - Notebooks can't open the DuckDB file while the app holds it for writing, so they call `nembot.client.query(sql)`. That hits the app's SELECT-only `POST /api/query` (Parquet response) and falls back to a read-only file connection when the app is down. `notebooks.py` starts JupyterLab / `marimo edit` as child processes on random localhost ports with tokens, on the first `/notebooks/open/<file>`, and stops them with the app.
   - Agent-written notebooks: `guides.py` serves reference material on demand. Each guide is `guide_files/<name>/GUIDE.md` (front matter `title`, one-line `summary`) plus `sections/*.md`; the prompt lists only the summaries (`prompt_index`) and the agent calls `read_guide(name, section?)`. Guides: `marimo` (nembot section plus text adapted from marimo-team/skills `marimo-notebook`; `sections/LIVE.md` adapted from marimo-team/marimo-pair; Apache-2.0, licences in `LICENSES/`) and `jupyter` (ipywidgets). `notebook_files.NotebookFiles` runs `write_notebook` (marimo: whole `.py` as `code`; Jupyter: `cells`) and `read_notebook`: nothing is saved until it passes `marimo check` (non-formatting issues) and a headless run (`python nb.py`), or for Jupyter `nbconvert --execute` (outputs kept), each in a subprocess with `NEMBOT_URL`/`NEMBOT_DATABASE` (which `nembot.client.query` reads as defaults); problems go back to the agent, an existing file needs `overwrite=true`, and the AEMO credit is appended as a last cell if missing. Charts aren't drawn in the check run, so altair's row limit (5,000; 20,000 in marimo) isn't caught; the guides tell agents to aggregate in SQL. `run_in_marimo(notebook, code)` uses marimo pair's transport against nembot's own marimo server (`NotebookServers.running('marimo')` gives port and token): `GET /api/sessions` to find the open notebook's session, then `POST /api/kernel/execute` (SSE stdout/stderr/done) running in the notebook's scratchpad, where `marimo._code_mode` (private, unstable) adds, edits and runs cells. The notebook must be open in a browser tab. Before agent code runs (`write_notebook` checks, `run_in_marimo`), interactive chats show an approval card (`chat.approve_code`: `code_request`/`code_decision` events, answered via `POST /api/chat/answer`); "Don't ask again" and the Settings switch set `confirm_code = false` in credentials.toml. When nembot starts marimo, `notebook_context.write_marimo_project` writes `<reports>/pyproject.toml`: `[tool.marimo.ai] rules` (a NEM primer plus the downloaded tables and columns, column descriptions dropped past `BUDGET`) and `[tool.marimo.runtime] auto_instantiate = true`. marimo merges these with the user's own settings (models and keys are untouched).
   - Plugins (`plugins.py`, `static/plugins.js`): folders in `--plugins-dir` (default `plugins/`) with `plugin.toml` plus optional `plugin.py` (`setup(nem)` registers `@nem.tool`, `@nem.route`, `nem.prompt`; `nem.query(sql)` returns polars), `client.js` (served wrapped in `nembot.definePlugin(name, fn)`; it gets a per-plugin API with `addTab`, `onChatEvent`, `addResultAction` and helpers) and `style.css`. Each reload imports `plugin.py` into a fresh module. A broken plugin is recorded with its traceback and never crashes the app. Plugin tool names are `<plugin>_<tool>`. Their results can include a `table` and custom `events` (`plugin_event`). A tab's `render(container, rest)` gets the rest of its address (`#plugin/<plugin>/<tab>/<rest>`), so tabs can have pages; `addResultAction(factory(result, question))` also gets the user's message; the client API exposes `sqlBlock`, `details`, `jsonTree` and `dataTable` (createDataTable). `client.query_parquet` returns a SELECT's raw Parquet bytes (`client.query` wraps it in polars).
   - Modes: a conversation is either `analyst` or `creator`, fixed for its lifetime. `chat.mode_setup()` builds the system prompt and tools per mode. The analyst sees plugin tools and their one-line notes, never the plugin API. `creator.py` holds Creator mode's prompt (the full plugin API reference) and tools: inspect_runtime, list/read/write/delete_plugin_file (drafts only, paths checked by `plugins.safe_path`), test_plugin (runs `python -I -m nembot.plugin_test` in a subprocess with a timeout; queries go through the app's `/api/query`) and install_plugin (approval card via `Conversation.pending`, then backup and reload). Providers take `system` and `tools` from `run_turn`.
   - Tables: `static/datatable.js` (`createDataTable`) is the shared table, ported from marimo's data table (Apache-2.0; attribution in its header, `LICENSES/` and the README). It also ports marimo's interactions: cell-range selection (a rectangle of anchor and focus over visible columns) with Count/Sum/Average stats and TSV copy, the right-click menu, filter pills plus an editor (operators and labels from marimo's `filters/operators.ts`), filter-by-values with top-30 counts, column visibility, wrap text, the row viewer, and column summaries in headers (`moSummarySpec` ports marimo's Vega-Lite histogram spec; charts render lazily with an IntersectionObserver and their DOM nodes are reused across redraws). "Chart this" (a nembot addition: the selection bar's Chart button or the right-click menu) opens a dialog with a Vega-Lite chart of the selected cells or of every row of the selected columns (up to `MO_CHART_ROWS` = 5000; server-side tables fetch them through `fetchPage`, and the explorer accepts that page size as `explorer.CHART_ROWS`). `moChartDefaults` guesses the chart (time x → line, categories → bar, averaging repeated categories) and the user can change chart type, x, series and aggregate; automatic choices follow the rows, picked ones stick. Mousedown on a cell calls `preventDefault()` (and tbody is `user-select: none`) so the browser's text selection never competes with the cell range. It runs client-side (search, filters, sort and export in JS; `moMatches` mirrors the server SQL) or server-side with `fetchPage({offset, limit, sort, search, filters})` and `fetchValues`. The explorer implements these via `q`, `filters` (JSON) and `sort`/`order` params on its rows endpoint plus `/api/explorer/tables/<name>/values` and `/summaries` (`explorer.summaries`: one aggregate scan for every column's stats, plus a UNION ALL for 9-bin histograms, skipped above `SUMMARY_ROW_LIMIT` = 1M rows), with SQL built by `explorer.conditions()`: catalogue column names only, values as parameters, marimo semantics (case-sensitive `contains`, inclusive `between`, `not_in` keeps nulls, case-insensitive literal search). Its styles are the `.mo-*` rules in `app.css`; keep them close to marimo's values.
   - Attribution: `attribution.CREDIT` is AEMO's required credit line. It appears in every report/notebook export, the README and the header's "Data: AEMO" dialog (`/api/about`). Keep it on any new export format.
   - The web chat's prompt and tools started as a copy of `load_mms.py` but have since moved on; the notebook is the legacy version.

## Evals

The eval set and its tooling are a private plugin in `plugins/evals/`, a separate git repository that this repo ignores (see its own `CLAUDE.md`). Keep eval questions, answers and eval-specific code out of this repo.

## Tests

`tests/test_chat.py` covers history rendering and the turn loop with a fake provider (no network). Loader tests run against real DuckDB in temp dirs with the network faked by patching `urllib.request.urlopen` to an in-memory NEMWEB server (`tests/test_ingest.py`: `MonthlyArchive` builds synthetic MMS ZIPs and listings). No test hits the real network.
