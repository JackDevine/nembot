# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Do not publish

**Do not push, publish or open pull requests for any of this work** until the licensing research is done: which licence nembot should use (the user is interested in CC BY-NC 4.0 with paid commercial licences, as OpenElectricity does), and the AEMO terms questions in `plan.md` → "Licensing". Commit locally only.

## Commands

Python >=3.14, managed with `uv`. Tests use stdlib `unittest` (no pytest).

```bash
uv run python -m unittest discover -s tests                  # all tests (plain `-m unittest` finds none)
uv run python -m unittest discover -s tests -k test_name      # single test by name substring
uv run python scripts/build_catalog.py                       # rebuild catalog.json from the data-model PDF
uv run nembot --start 2026-06-01 --end 2026-08-31            # load data (defaults: data/nem.duckdb, data/cache)
uv run nembot-chat                                           # web chat at http://127.0.0.1:8000 (--port, --database)
uv run marimo edit load_mms.py                               # original notebook chat (OpenRouter)
```

`load_mms.py` imports `polars` and `pydantic_ai`, which are **not** declared in `pyproject.toml`; supply them (e.g. `uv run --with polars --with pydantic-ai ...`) to run the notebook. The web chat needs only declared deps plus Anthropic credentials (`ant auth login` profile or `ANTHROPIC_API_KEY`).

## Architecture

Three pieces share the DuckDB file `data/nem.duckdb` (`data/` and `__marimo__/` are gitignored):

1. **`src/nembot/` — the ingest package** (public API: `load_mms`, CLI: `nembot`).
   - `catalog.json` + `catalog.py` — the data-model catalogue for all 571 tables: package, comment, description, visibility, primary key, indexes, columns with Oracle and DuckDB types, and whether the latest MMSDM monthly archive publishes the table. It's generated from AEMO's Electricity Data Model Report **PDF** by `uv run python scripts/build_catalog.py` (pdfplumber is a dev dependency; the build takes about 2 minutes, needs network, and fails loudly via `problems`). Never hand-edit the JSON. One data-model version (currently 5.7) is used for both docs and loader schemas.
   - `tables.py` — `Table` schemas generated from the catalogue: ordered columns → DuckDB types, plus the primary key. The CSV envelope identity (dataset/csv_table) is only known for the four `DEFAULT_TABLES`; for other tables `nemweb.normalize` takes it from the archive's first `I` record and errors if an archive mixes tables. The loader accepts only `ingest.SUPPORTED` tables until its window filtering is generalised.
   - `nemweb.py` — all HTTP goes through `_polite()` → `_open()`, a shared keep-alive urllib3 pool that raises urllib-style `HTTPError`/`URLError`. Tests patch `nembot.nemweb._open` with a fake NEMWEB server. A process-wide `_Throttle` allows `CONCURRENCY` requests (default 2, env `NEMBOT_CONCURRENCY`, capped at 3) and paces request starts AutoThrottle-style (latency ÷ concurrency, with optional floor `REQUEST_INTERVAL`). Errors (429/5xx/connection) drop to one request at a time with backoff and `Retry-After`, recovering after `RECOVER_AFTER` successes; `FORBIDDEN_LIMIT` consecutive 403s abort the run. `download_many()` downloads a few files ahead in parallel and yields them in order; both loaders use it. Directory listings are cached in memory for an hour (tests call `nemweb.clear_cache()`). It scrapes MMSDM HTML directory listings to discover monthly per-table ZIPs, downloads them into `cache_dir` (validated, SHA256'd, reused on rerun), and `normalize()` strictly validates the MMS C/I/D CSV envelope (opening C record, END OF REPORT count, integer versions, known columns, PK present), emitting one clean CSV per `I` header segment.
   - `ingest.py` — orchestration. Market time is fixed UTC+10. Each (table, file) is loaded in its own transaction and recorded in `_nembot.files` keyed by (url, sha256, table, window) so reruns skip completed work and interrupted runs resume. `_merge` stages typed CSVs, picks the latest `LASTCHANGED` per PK, raises on equal-`LASTCHANGED` conflicts (both within a file and against stored rows), and only updates rows with strictly newer `LASTCHANGED`.
   - `DUDETAILSUMMARY` is special-cased: it's effective-dated reference data, so all monthly snapshots are reconciled together in a temp `_reference` table *before* the date-window overlap filter is applied (otherwise later closures could resurrect old rows). Interval tables are window-filtered per file.
   - `cli.py` — argparse + TOML config (`--config`); config keys mirror flags, flags override config, and config is validated even when overridden.
   - `load_mms()` loads any table in `ingest.SUPPORTED` (every catalogue table the monthly archive publishes). `EXACT_WINDOW` tables (DISPATCHPRICE, DISPATCHREGIONSUM, DISPATCH_UNIT_SCADA) are filtered to the exact market days requested; every other table loads **whole archive months** (the file log records month windows), because timestamp meanings vary by table. Tables without `LASTCHANGED` are updated by the most recently loaded archive. Timestamps parse with or without milliseconds (`TIMESTAMP(n)` columns).
   - With no `connection=`, `load_mms()` opens and returns a writable connection the caller must close. With one (the web app), it runs on a cursor of that connection and returns it. `progress=` receives stage events and `cancel=` (a `threading.Event`) aborts with `nemweb.Cancelled`. Each file commits on its own, so finished files survive a cancel or a failure. DuckDB allows one writer per database file, so the CLI can't run while the web app has the database open. The web app checkpoints on shutdown so restarts don't depend on replaying the WAL: DuckDB 1.5 writes an unreplayable WAL for `ALTER TABLE` on a table whose rows are still only in a replayed WAL, so don't add ALTER-based migrations to the `ensure()` functions (temp tables are fine).

   - `live.py` — recent data from NEMWEB's report feeds (newer than the monthly archive) for the tables in `FEEDS`, each mapped to a report family, file prefix and CSV identity (verified against live files). An ARCHIVE file covers from its date to the next archive file's date, or to an explicit second date for weekly files. Separate filename series, e.g. rooftop MEASUREMENT vs SATELLITE, are handled independently. CURRENT files fill in after the newest archive, but only up to `CURRENT_LIMIT` (600) requests; beyond that the plan stops at the archive's end and reports `skipped_current`. `nemweb.normalize` descends into nested ZIPs (daily archives hold 288 interval ZIPs), merges all members into one output per table version, and with `required=False` tolerates files without the table. Live files are logged in `_nembot.files` with their coverage window. "Loaded through" comes from the table's own max time column, not from file URLs.

2. **`load_mms.py` — a marimo notebook** (despite the name, it does not load data). It opens the DB `read_only=True` and runs a pydantic-ai agent (via OpenRouter, `OPENROUTER_API_KEY`) inside `mo.ui.chat`, exposing two tools: `query_mms(sql)` and `visualize_mms(sql, plot_spec)` (Vega-Lite validated with Altair before running SQL, rendered to PNG for the model). The `SYSTEM_PROMPT` cell defines agent behavior.

3. **The web chat** (`nembot-chat`): a port of the notebook that can use any Claude model directly or any tool-capable OpenRouter model, switching freely mid-conversation.
   - `chat.py` — the provider-neutral core: system prompt (vision and text-only variants), tool schemas, DuckDB tool execution, and `run_turn` (the tool loop, sequential tool calls, rollback of a failed turn). History is stored in a **neutral format** (documented at the top of the file); plot PNGs are always stored and only sent to models that can read images.
   - `claude.py` / `openrouter.py` — each provider renders neutral history into its wire format and streams one assistant turn. Rendering must stay **deterministic per (history, current model)** so turns replay byte-identically (prompt caching, and Claude's preserved-thinking check). Same-model turns replay provider raw data (Claude content blocks with thinking; OpenRouter `reasoning_details`); turns from other models are rendered from neutral fields and prefixed `[Earlier reply by …]`. Claude per-model request features (adaptive thinking, `display: "updates"`, effort, `fallbacks: "default"`) are gated by `request_options()`.
   - Web search (UI toggle, default on) adds Anthropic's server-side `web_search`/`web_fetch` tools (`_20260209` dynamic-filtering versions where supported, gated in `claude.web_tools()`) or OpenRouter's `openrouter:web_search` server tool. Neither runs in our tool loop. Sources are emitted as a `sources` event: Claude citations, or the consulted pages when dynamic filtering leaves the text uncited.
   - `models.py` — the model catalogue (Anthropic models API + public OpenRouter `/models`, cached for an hour). Model refs are `claude:<id>` / `openrouter:<id>`.
   - `downloads.py` — in-memory download jobs (`kind` 'archive' for monthly MMSDM, 'live' for `live.load`; `submit_live()` plans and queues the recent files) run one at a time by a worker thread via `load_mms` on the app's single read-write connection (chat/explorer reads use their own cursors and see each committed file). It also provides `plan()` (loaded months from `_nembot.files` URLs, latest published month, refresh range, size estimate from listing sizes) and the freshness flags shown in the explorer. Jobs are not resumed after a restart.
   - `web.py` (Starlette) streams UI events as SSE to `static/index.html` (vega-embed, marked, DOMPurify from CDN). Conversations are keyed by a browser-generated id; they are held in memory while in use and saved by `chats.py` (below). OpenRouter needs `OPENROUTER_API_KEY`.
   - `explorer.py` — the read-only explorer API: overview (catalogue tables in the monthly archive, marked downloaded or not), table details (docs, row count, time-column range, `_nembot.files` download history, filter options) and paged rows. Column names in SQL only ever come from the catalogue; filter values are always parameters. `catalog.time_column()`/`kind()` classify tables as interval, effective-dated or reference.
   - Front end: `static/index.html` is a shell with hash routing (`#chat/<id>`, `#explorer/<TABLE>`, `#docs/<id>`, `#snippets/<id>`, `#reports`). The code lives in classic scripts that share globals, loaded in order: `common.js` (helpers), `datatable.js`, `downloads.js` (job polling, header indicator, progress/error panel, month-range dialog), `chat.js`, `explorer.js`, `snippets.js`, `docs.js`, `chats.js`, `reports.js`, `plugins.js`, plus `app.css`. Plugin tabs route as `#plugin/<plugin>/<tab>`; the management page is `#plugins`. SQL is shown with `codeBlock(code, 'sql')` in `common.js` (`sqlBlock` uses it): CodeMirror's Lezer SQL parser from esm.sh, mapped to marimo's editor colours (`--tok-*` in `app.css`, light and dark). Vega-Lite specs use `jsonTree(value)`, a collapsible tree (`<details>` per object/array, Alt+click folds a whole branch) in the same colours. Charts go through `embedChart`, which redraws them when the light/dark setting changes.
   - Missing data: `describe_table` documents any catalogue table. `request_download` emits a `download_request` event (an approval card in chat), then waits on a Future in `Conversation.pending`, which `POST /api/chat/decision` resolves. On approval it submits a normal download job, streams progress and returns a result telling the model to re-run its query. Each user message stores a frozen `<data_status>` note (`chat.data_status`) of what's downloaded; it's rendered after the user's text and never recomputed, so history replays identically. The archive table list sits in the static system prompt.
   - `chats.py` — saved chats in `chats.chats`, written after every turn by the chat endpoint: the neutral `history` (replayed to the model when the chat continues, including after a restart), `results` (R ids) and a `transcript` of what the UI showed (`{'text', 'events'}` per turn, compacted by `chats.compact`), which `static/chats.js` replays through `renderTurn(text, {replay: true})` (no side effects; old approval cards are disabled). `web_search` is restored on reopening, because Claude's preserved thinking is bound to the same system prompt and tools. A new chat is named by its model from the first message in parallel with the reply (`chat_title` event); a title the user typed (`title_by_user`) is never overwritten. The Chats column (search, ✎/double-click rename, delete) routes as `#chat/<id>`. Each chat shown in a session has its own pane in `#log` (`panes` in chat.js), so replies keep streaming into their chat while another is on screen; busy chats keep their live pane, finished hidden panes are dropped and replayed from the saved chat if reopened, and the list marks chats that are replying or waiting for an approval (`pane.busy`/`pane.waiting`). Approval cards post their own chat id.
   - `snippets.py` — saved SQL plus an optional Vega-Lite spec (no data) in the `snippets.snippets` table of the same database, created on startup. They're re-run on every open (`/api/snippets/{id}/run`). Names come from the current chat model via each provider's `complete()`, falling back to the table name. `static/snippets.js` adds the "☆ Add to snippets" button to chat results and the Snippets page.
   - Shared documents (`docs.py`, `static/docs.js`): Tiptap (MIT, loaded from esm.sh on first open via dynamic `import()`) rich-text docs in the `docs` schema: `docs.docs` stores Tiptap JSON plus comment threads (JSON), `docs.images` stores pasted/uploaded images (PNG/JPEG/GIF/WebP, never SVG). The browser is the source of truth and autosaves the whole doc; only one editor is open per document (Docs page `#docs/<id>` or the panel beside the chat). Tables and charts are `dataBlock` nodes holding their SQL, spec and a row **snapshot** (`docs.snapshot`; Refresh re-runs it). Highlighting text and choosing "Ask nembot" runs a one-off `run_turn` in `doc` mode with a `DocSession`: the request carries the document as numbered blocks (`[B3]`), and nembot proposes changes with `suggest_edit`/`suggest_insert`/`suggest_table`/`suggest_chart`, which the browser applies as tracked suggestions (`suggestInsert`/`suggestDelete` marks, or a `suggestion` attribute on whole blocks) for the user to accept or reject. Everything nembot writes into a document (insertions, inline rewrites, create_document seeds) travels as **markdown and is rendered in the browser with `marked`**, the chat's renderer, so GFM tables and lists format exactly as in the chat; the editor has Tiptap tables. Inserted content is parsed with `createNodeFromContent` and inserted in one transaction so its size is exact (Tiptap's trailing-node plugin appends steps afterwards). Suggested whole blocks are outlined by a decoration (`nb-suggested-block`), since the table node view ignores attributes. In the main chat, `create_document(title, content)` seeds a doc from markdown with `[[R3]]` lines (`seed`: JSON parts, converted once by the editor), and results get "＋ Add to doc".
   - Reports: each successful query/plot result gets an id (`R1`, … in `Conversation.results`, shown in its tool output and UI). `create_report(format, title, content)` takes markdown with `[[R3]]` lines. `reports.py` re-runs the referenced SQL and builds html (interactive vega-embed), pdf (WeasyPrint, static PNGs), docx, pptx (a slide per `##` section), xlsx (a sheet per result) or Jupyter/marimo notebooks into `<database dir>/reports/`.
   - Notebooks can't open the DuckDB file while the app holds it for writing, so they call `nembot.client.query(sql)`. That hits the app's SELECT-only `POST /api/query` (Parquet response) and falls back to a read-only file connection when the app is down. `notebooks.py` starts JupyterLab / `marimo edit` as child processes on random localhost ports with tokens, on the first `/notebooks/open/<file>`, and stops them with the app.
   - Plugins (`plugins.py`, `static/plugins.js`): folders in `--plugins-dir` (default `plugins/`) with `plugin.toml` plus optional `plugin.py` (`setup(nem)` registers `@nem.tool`, `@nem.route`, `nem.prompt`; `nem.query(sql)` returns polars), `client.js` (served wrapped in `nembot.definePlugin(name, fn)`; it gets a per-plugin API with `addTab`, `onChatEvent`, `addResultAction` and helpers) and `style.css`. Each reload imports `plugin.py` into a fresh module. A broken plugin is recorded with its traceback and never crashes the app. Plugin tool names are `<plugin>_<tool>`. Their results can include a `table` and custom `events` (`plugin_event`).
   - Modes: a conversation is either `analyst` or `creator`, fixed for its lifetime. `chat.mode_setup()` builds the system prompt and tools per mode. The analyst sees plugin tools and their one-line notes, never the plugin API. `creator.py` holds Creator mode's prompt (the full plugin API reference) and tools: inspect_runtime, list/read/write/delete_plugin_file (drafts only, paths checked by `plugins.safe_path`), test_plugin (runs `python -I -m nembot.plugin_test` in a subprocess with a timeout; queries go through the app's `/api/query`) and install_plugin (approval card via `Conversation.pending`, then backup and reload). Providers take `system` and `tools` from `run_turn`.
   - Tables: `static/datatable.js` (`createDataTable`) is the shared table, ported from marimo's data table (Apache-2.0; attribution in its header, `LICENSES/` and the README). It also ports marimo's interactions: cell-range selection (a rectangle of anchor and focus over visible columns) with Count/Sum/Average stats and TSV copy, the right-click menu, filter pills plus an editor (operators and labels from marimo's `filters/operators.ts`), filter-by-values with top-30 counts, column visibility, wrap text, the row viewer, and column summaries in headers (`moSummarySpec` ports marimo's Vega-Lite histogram spec; charts render lazily with an IntersectionObserver and their DOM nodes are reused across redraws). Mousedown on a cell calls `preventDefault()` (and tbody is `user-select: none`) so the browser's text selection never competes with the cell range. It runs client-side (search, filters, sort and export in JS; `moMatches` mirrors the server SQL) or server-side with `fetchPage({offset, limit, sort, search, filters})` and `fetchValues`. The explorer implements these via `q`, `filters` (JSON) and `sort`/`order` params on its rows endpoint plus `/api/explorer/tables/<name>/values` and `/summaries` (`explorer.summaries`: one aggregate scan for every column's stats, plus a UNION ALL for 9-bin histograms, skipped above `SUMMARY_ROW_LIMIT` = 1M rows), with SQL built by `explorer.conditions()`: catalogue column names only, values as parameters, marimo semantics (case-sensitive `contains`, inclusive `between`, `not_in` keeps nulls, case-insensitive literal search). Its styles are the `.mo-*` rules in `app.css`; keep them close to marimo's values.
   - Attribution: `attribution.CREDIT` is AEMO's required credit line. It appears in every report/notebook export, the README and the header's "Data: AEMO" dialog (`/api/about`). Keep it on any new export format.
   - The web chat's prompt and tools started as a copy of `load_mms.py` but have since moved on; the notebook is the legacy version.

## Tests

`tests/test_chat.py` covers history rendering and the turn loop with a fake provider (no network). Loader tests run against real DuckDB in temp dirs with the network faked by patching `urllib.request.urlopen` to an in-memory NEMWEB server (`tests/test_ingest.py`: `MonthlyArchive` builds synthetic MMS ZIPs and listings). No test hits the real network.
